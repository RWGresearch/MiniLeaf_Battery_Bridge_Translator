# Manual Verification Checklist

**Working document, not a finished reference.** Mirrors
`Refrance/Leaf_BMS_Emulator/battery emulator overview/10-manual-verification-checklist.md` — a
per-feature checklist for going back through what's been personally tested against real hardware
(RZ450e bench pack + real Leaf car) vs. what's only documented/researched. Fill this in as testing
happens; findings get folded back into `05-battery-management-safety.md` (promoting a researched
default to "user-confirmed," correcting anything wrong, flagging untested items as still open) —
same discipline both reference projects already use.

Status values: **Documented** (researched/inherited, not yet tested on this specific setup),
**Needs Validation** (tested once, result unclear or contradicts the default), **Confirmed** (user
personally tested and signed off).

## Battery management features (`05-battery-management-safety.md`)

| Feature | Default | Status | Notes |
|---|---|---|---|
| Low-voltage cutoff (3.00V, `capacity_empty`), cell-voltage authoritative | 3.00V/cell | Confirmed (software) | **Safety bug found and fixed 2026-07-31**: SoC used to be OR'd in as an equal independent trigger, so a low SoC reading alone could cut off the pack even with every cell healthy. Reproduced directly (3.50V cells + 5% SoC → incorrectly cut off before the fix) and confirmed fixed (same scenario now stays 0, with a visible "SoC backup check does not confirm" warning instead of acting). Also verified the reverse (low cells + healthy SoC still correctly cuts off) and the agreement case. Still needs a real discharge test down near 3.00V/cell to confirm the threshold itself, separate from the trigger-logic fix. |
| Low-voltage soft-cut persistence window (2.0s) | 2.0s | Confirmed (software) | **Added 2026-07-31** (docs/12 finding F5). Unit-tested (`tests/test_management_engine.py`): a cell held at 2.90V does NOT latch `capacity_empty` on the first tick, but does latch once the condition has persisted past 2.0s; a cell at 2.70V (below the emergency floor) triggers the hard cut instantly with no persistence delay, confirming the two tiers behave differently as designed. Still needs a real spike-load test (hard acceleration on a marginal pack) to confirm 2.0s is the right real-world window - too short doesn't guard against real sag transients, too long delays a genuine cutoff. |
| Emergency low-voltage (2.80V, hard cut) | 2.80V/cell | Documented | Not yet tested. |
| Charge/regen power limit + AC charge target (proactive 3.90V full → 4.10V zero, 4.30V emergency, 80%/100% SoC stop) | 3.90/4.10/4.30V/cell, 80/100% | Documented | **Corrected 2026-07-31 (twice)**: taper driven purely by continuous per-cell voltage (not gated by SoC), confirmed to double as the regen-braking power limit while driving (`charge_limit_kw` is the Leaf's shared "Charge/regen power limit" field), and reworked to a wide, proactive curve (user-specified: full regen ≤3.90V, zero ≥4.10V) specifically because the real VCM is slow to respond to a `charge_limit_kw` change. Unit-tested the exact curve (100%/75%/50%/25%/0% at 3.90/3.95/4.00/4.05/4.10V). Still needs a real charge session AND a real regen event (e.g. descending a hill near-full) to confirm the curve is actually wide/early enough against the real VCM's response lag. |
| `full_charge_flag` charging-context gate (`charge_permission_input`) | gated, off by default | Confirmed (software) | **Safety bug found and fixed 2026-07-31**: `full_charge_flag` (instant contactor drop on the real Leaf) previously fired from SoC alone with no charging-context check, which would have dropped HV contactors while simply driving above the target SoC. Reproduced directly (85% SoC, not charging → `full_charge_flag` incorrectly set before the fix) and confirmed fixed (same scenario now stays 0; only fires when `charge_permission_input` is active). Verifiable in software alone - re-verify once running against a real charge session that a legitimate stop still fires correctly. |
| Emergency high-voltage (4.30V, hard cut) | 4.30V/cell | Documented | Not yet tested. |
| Over-temperature derate, restructured (cold-derate 10/0°C on coldest probe, charge 32/45°C, discharge 55/60°C on hottest probe, all soft) | see `05-...md` | Documented (bug fix confirmed in software) | **Restructured 2026-07-31** (docs/12 findings F1/F3/F6). **Bug fixed and confirmed** (`tests/test_management_engine.py`): the cold-side charge block previously tested the hottest probe, so a pack with a frozen coldest cell but a warm hottest cell would still accept charge - unit-tested directly (hottest 70°F / coldest 20°F → charge correctly blocked; the reverse scenario → charge correctly NOT blocked) and confirmed fixed. Added a cold-side derate ramp (10°C→0°C) unit-tested at the midpoint (41°F → ~50% factor). General NMC research, not RZ450e-specific — the temperature values themselves still need real thermal testing. |
| Emergency temp (65°C/149°F, hard cut, hottest probe) | 149°F | Confirmed (software) | **Added 2026-07-31** (docs/12 finding F6) - previously, hitting the soft `discharge_hard_stop_f`/`charge_hard_stop_f` values directly asserted a hard cut, with no separate emergency tier (inconsistent with this feature's own "Soft (ramp)" documentation). Unit-tested: at exactly 140°F (the old combined threshold), discharge power now correctly reaches zero WITHOUT a hard cut firing; at 150°F (above the new 149°F emergency tier), a hard cut correctly fires. Value itself (149°F) is researched, not yet tested against a real thermal event on this pack. |
| Staleness watchdog (60s soft, +5s hard) | 60s / 65s | Documented | Needs a deliberate CAN-disconnect test to confirm the escalation actually fires as designed. |
| Discharge power taper (proactive 3.50V full → 3.00V zero, fast-attack/slow-release hysteresis) | 3.50/3.00V/cell, 3.0s recovery | Documented | **Reworked 2026-07-31**: now per-cell-voltage-driven (not SoC) with fast-attack/slow-release hysteresis, mirroring the charge/regen taper. Unit-tested the curve (100/80/50/20/0% at 3.60/3.40/3.25/3.10/3.00V) and the hysteresis directly (a sudden dip to 3.00V snapped discharge power to 0 instantly; recovering to 3.60V climbed back to full only gradually over the configured recovery-ramp time, not instantly). Still needs a real discharge test under actual acceleration load to confirm the 0.50V window is wide enough for real-world cell sag, and that the 3.0s recovery time doesn't feel too sluggish or too twitchy in practice. |
| Cell imbalance monitor (50mV warn, monitor only) | 50mV | Confirmed (software) | **Added 2026-07-31** (docs/12 finding F4). Unit-tested: a 100mV artificial spread correctly triggers the warning text, a balanced pack (0mV spread) correctly reports "ok," and the monitor never asserts `capacity_empty`/`relay_cut_request` under any spread (monitor-only by design, verified). The 50mV threshold itself is a general industry figure, not tuned against this specific pack's real cell-to-cell variance over time. |
| Overcurrent monitor (150A discharge / 30A charge-regen warn, monitor only) | 150A / 30A | Documented (software-verified logic) | **Added 2026-07-31** (docs/12 finding F2). Unit-tested: elevated current doesn't warn on the first tick (persistence guard confirmed), does warn once sustained past the 5.0s persistence window, never derates/cuts power under any current reading (monitor-only, verified), and the saturation note correctly appears at/near the `0x023` sensor's ±204.7A ceiling. The threshold VALUES are provisional pending real drive-cycle current logging (see `10-open-questions.md` #8) - no cell datasheet exists for this pack, so these are derived from this project's own sensor/charger specs, not a manufacturer limit. |
